== Архитектура ПО

=== Общая архитектура ПО

Программное обеспечение устройства измерения влажности почвы построено по модульному принципу и разделено на несколько логических уровней. Такой подход обеспечивает независимость прикладной логики от аппаратной части, упрощает тестирование отдельных компонентов и позволяет модифицировать систему без изменения основной архитектуры.

Архитектура состоит из трёх основных уровней:

* уровень аппаратного взаимодействия (`AbstractHardware`);
* уровень интерфейсов (`appContracts`);
* уровень реализации (`Implementation`).

.Общая архитектура ПО
image::9.jpg[]

Система построена на двух параллельных задачах реального времени (FreeRTOS):

* `MeasurementTask` — измерительная задача с периодом 100 мс и максимальным приоритетом
* `PCTask` — задача отправки данных с периодом 1000 мс и минимальным приоритетом

Взаимодействие между задачами осуществляется через общее хранилище данных `DataStorage`, которое работает по принципу «почтового ящика»: одна задача записывает, другая читает.

=== Шаг 1: Инициализация системы (выполняется один раз при старте)

====  Настройка АЦП и DMA

При запуске задачи `MeasurementTask` вызывается метод `Config()` у `AdcDmaDataProvider`.

Настройка включает два этапа:

* **Настройка DMA:** выбирается канал (0), устанавливается циркулярный режим (после заполнения начинает заново), задаётся направление передачи (от периферии в память), указывается адрес регистра данных АЦП и адрес переменной, куда сохранять результаты

* **Настройка АЦП:** устанавливается разрешение 12 бит, включается непрерывный режим (измеряет без остановки), активируется DMA, подаётся питание на АЦП и запускается преобразование

**Результат:** АЦП постоянно измеряет сигнал с датчика, а DMA автоматически сохраняет каждое новое значение в переменную `data`. Процессор при этом свободен.

==== Настройка USART для Bluetooth

Настройка USART выполняется **один раз** до запуска задач FreeRTOS (например, в функции `main()` до вызова `StartScheduler()`).

Конфигурация включает:

* Пины: TX — PA2, RX — PA3
* Скорость: 9600 бод
* 8 бит данных
* Один стоп-бит
* Контроль чётности отключён

Так как эти настройки никогда не меняются в процессе работы, нет смысла вызывать `ConfigUSART()` при каждом запуске `PCTask` или `BluetoothTask`.

**Результат:** USART настроен единожды и готов к передаче данных через Bluetooth-модуль.

=== Шаг 2: Работа измерительной задачи (каждые 100 мс)

Задача `MeasurementTask` выполняет следующие действия последовательно:

==== Запрос сырых данных

`MeasurementTask` обращается к интерфейсу `IMeasurementVariable` и просит дать измеренное значение.

А объект `Voltage`, который сидит за этим интерфейсом, берёт сырые данные у `IDataProvider`, превращает их в напряжение и возвращает результат.

Так что задача даже не знает, откуда берутся данные — она просто стучится в `IMeasurementVariable`, а всё остальное происходит под капотом.

**Результат:** Получено сырое значение АЦП в диапазоне от 0 до 4095.

==== Преобразование в напряжение

Объект `Voltage` переводит сырой код АЦП (0..4095) в напряжение

Параметры `gain` и `offset` передаются как шаблонные аргументы при создании объекта. В данной конфигурации:

* `gain = 0.000806206`
* `offset = 0`

Это обеспечивает соответствие: код 4095 → 3.3 В, код 0 → 0 В.

**Результат:** Получено напряжение в вольтах (0..3.3 В).

==== Фильтрация значения

Отфильтрованное значение = старое значение + (новое значение - старое значение) × коэффициент фильтра.

Коэффициент фильтра вычисляется как:

stem:[\tau = 1 - \exp\left(-\frac{\Delta t}{RC}\right)]

где:

* stem:[\Delta t = 0.1] с — период измерений
* stem:[RC = 5.0] — постоянная времени фильтра

Первый вызов просто запоминает значение без фильтрации.

**Результат:** Получено сглаженное напряжение без резких скачков и шумов.

==== Расчёт влажности в процентах

Объект `Humidity` переводит напряжение в проценты по кубической калибровочной формуле:

Процент = a3 × напряжение³ + a2 × напряжение² + a1 × напряжение + a0

Коэффициенты подобраны экспериментально для конкретного датчика. Если результат превышает 100%, он ограничивается 100%.

**Результат:** Получена влажность почвы в процентах (0..100%).

==== Сохранение в хранилище

=== Сохранение в хранилище

Объект `DataStorage` сохраняет полученное значение вместе с метаданными:

* **Название переменной** — `"Humidity"`
* **Значение** — рассчитанный процент влажности
* **Единицы измерения** — `"%"`

Структура хранения:

[source,cpp]
----
struct DataPoint {
  const char* name;      // "Humidity"
  float value;           // 0..100
  const char* unit;      // "%"
};
----

Хранилище сохраняет эти данные в своей приватной переменной. При чтении другая задача (`PCTask` или `BluetoothTask`) получает полную информацию, а не просто безликое число.

**Результат:** В хранилище лежат именованные данные с единицами измерения, готовые к форматированию и отправке.

==== Ожидание следующего цикла

Задача засыпает на 100 миллисекунд, после чего цикл повторяется с шага 2.3.1.

=== Шаг 3: Работа задачи отправки (каждую секунду)

Задача `PCTask` выполняется с меньшим приоритетом, чтобы не мешать измерениям. Её работа состоит из следующих шагов:

==== Чтение данных из хранилища

Задача вызывает метод `GetData()` у объекта `DataStorage`. Тот возвращает текущее значение `mValue`, которое было туда записано задачей `MeasurementTask`.

**Результат:** Получена последняя измеренная влажность в процентах.

==== Преобразование числа в строку

Объект `Usart` преобразует число влажности в строку с двумя знаками после запятой. Например, число 45.6789 превращается в строку «45.68».

**Результат:** Число готово к вставке в текстовое сообщение.

==== Формирование и отправка сообщения

Задача `PCTask` (или `BluetoothTask`) получает из `DataStorage` значение влажности и передаёт его в `Formatter`.

Объект `Formatter` собирает строку по шаблону:

[source,text]
----
Влажность почвы: XXX.XX %
----

Затем строка отправляется через USART2. Метод отправляет каждый символ по очереди, дожидаясь готовности передатчика перед каждым символом.

**Результат:** Сообщение уходит через Bluetooth-модуль на подключённый компьютер или телефон.

==== Ожидание следующей отправки

Задача засыпает до следующей секунды (интервал 1000 мс), после чего цикл повторяется с шага 2.4.1.

==== Уровень аппаратного взаимодействия (AbstractHardware)

Нижний уровень архитектуры отвечает за непосредственную работу с периферийными модулями микроконтроллера STM32F411.

На данном уровне располагается модуль `AdcDma`, реализующий:

* настройку встроенного АЦП;
* организацию непрерывного измерения;
* передачу данных через DMA;
* взаимодействие с регистрами микроконтроллера.

Модуль скрывает аппаратные особенности STM32 и предоставляет прикладному уровню готовые данные измерений через абстрактные интерфейсы.

Использование отдельного аппаратного уровня позволяет изолировать код работы с регистрами микроконтроллера от бизнес-логики приложения.

==== Уровень интерфейсов (appContracts)

Уровень `appContracts` содержит набор абстрактных интерфейсов, определяющих взаимодействие между компонентами системы.

На данном уровне отсутствует конкретная реализация алгоритмов. Интерфейсы описывают только контракт взаимодействия между модулями.

В архитектуре используются следующие интерфейсы:

[cols="1,3", options="header"]
|===
| Интерфейс | Назначение

| `IDataProvider`
| Получение сырых данных измерений с АЦП

| `IMeasurementVariable`
| Преобразование кодов АЦП в физические величины

| `IFilter`
| Интерфейс цифровой фильтрации измерений

| `IHumidity`
| Вычисление влажности почвы

| `IDataSetter`
| Сохранение результатов измерений

| `IUsart`
| Передача данных через интерфейс USART2

| `IThread`
| Абстракция задачи операционной системы FreeRTOS

| `IConfiguratorUsart`
| Форматирование строки перед передачей
|===

Использование интерфейсов позволяет:

* уменьшить связанность компонентов;
* упростить замену отдельных модулей;
* обеспечить расширяемость программного обеспечения;
* реализовать принципы объектно-ориентированного проектирования.

==== Уровень реализации (Implementation)

На уровне `Implementation` располагаются конкретные реализации интерфейсов прикладного уровня.

Основные компоненты:

[cols="1,3", options="header"]
|===
| Компонент | Назначение

| `AdcDmaDataProvider`
| Получение данных АЦП через DMA

| `Voltage`
| Преобразование кодов АЦП в напряжение

| `DigitalFilter`
| Реализация экспоненциального цифрового фильтра

| `Humidity`
| Расчёт влажности почвы по калибровочной формуле

| `DataStorage`
| Хранение результатов измерений

| `Usart`
| Передача данных через USART2

| `ConfiguratorUsart`
| Формирование строки для передачи по Bluetooth
|===

Каждый компонент реализует соответствующий интерфейс из уровня `appContracts`.

==== Задача MeasurementTask

Задача `MeasurementTask` отвечает за полный цикл обработки измерений влажности почвы.

Последовательность работы задачи:

. Получение сырых данных АЦП через `IDataProvider`.
. Преобразование данных в напряжение.
. Вычисление влажности почвы.
. Фильтрация измеренного значения.
. Сохранение результата в хранилище данных.

Задача выполняется периодически с интервалом **100 мс** в соответствии с требованиями технического задания.

==== Задача CommunicationTask

Задача `CommunicationTask` (в исходном тексте `PCTask`) отвечает за передачу информации на внешнее устройство через Bluetooth-модуль HC-06.

Основные функции задачи:

* получение актуальных данных из хранилища;
* форматирование строки вида:
+
[source,text]
----
Влажность почвы: XXX.XX %
----
* передача строки через USART2.

Передача выполняется с использованием интерфейса `IUsart`.

==== Принцип взаимодействия компонентов

Работа системы начинается с непрерывного измерения аналогового сигнала датчика влажности встроенным АЦП микроконтроллера STM32F411. Полученные данные автоматически передаются в память с помощью DMA.

Задача `MeasurementTask` периодически получает последнее измеренное значение, выполняет его обработку и сохраняет рассчитанную влажность в хранилище данных.

Задача `CommunicationTask` независимо от измерительного контура считывает подготовленные данные, преобразует их в текстовый формат и передаёт через Bluetooth-модуль HC-06 на ПК или мобильное устройство.

Таким образом, архитектура программного обеспечения обеспечивает:

* разделение ответственности между модулями;
* независимость прикладной логики от аппаратной платформы;
* возможность расширения функциональности;
* поддержку многозадачности средствами FreeRTOS;
* стабильную обработку и передачу данных в реальном времени.
